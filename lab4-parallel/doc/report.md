## 1 Цель работы

Познакомиться с инструментами, направленными на решение задач, использующих технологии распараллеливания, и сравнить последовательную и параллельную обработку запросов.

## 2 Постановка задачи и исходные данные

Необходимо смоделировать ситуацию, когда несколько пользователей почти одновременно обращаются к серверу. Запросы поступают на обработку и выстраиваются в очередь.

Рассматриваются три действия:

| Действие | Описание | Нагрузка на процессор |
|---|---|---:|
| 1 | Регистрация на портале | около 25% |
| 2 | Получение главной страницы | около 15% |
| 3 | Просмотр перечня зарегистрированных пользователей | около 1% |

Количество пользователей обозначается `U1`, `U2`, `U3`, время обработки одного запроса — `T1`, `T2`, `T3`.

Требуется сравнить четыре варианта:

1. последовательная обработка;
2. параллельная обработка с помощью `subprocess`;
3. обработка с помощью потоков `threads`;
4. асинхронная обработка с помощью `asyncio`.

### 2.1 Параметры эксперимента

Для демонстрационного запуска выбраны следующие значения (их можно изменить при запуске программы):

| Параметр | Значение |
|---|---:|
| U1 — регистрация | 3 пользователя |
| U2 — главная страница | 3 пользователя |
| U3 — список пользователей | 3 пользователя |
| T1 — регистрация | 1,0 с |
| T2 — главная страница | 0,7 с |
| T3 — список пользователей | 0,3 с |

Всего обрабатывается 9 запросов. Время обработки моделируется функцией ожидания `sleep`. Проценты загрузки процессора из условия выводятся как параметры действий, но фактическая загрузка CPU программой не измеряется и искусственно не создаётся. Такой подход позволяет просто сравнить способы организации одновременного ожидания запросов.

## 3 Описание алгоритмов

### 3.1 Последовательная обработка

Запросы обрабатываются один за другим. Следующий запрос начинает выполняться только после завершения предыдущего.

Общее время в модели без учёта накладных расходов:

`T = U1 · T1 + U2 · T2 + U3 · T3`.

Для выбранных значений:

`T = 3 · 1,0 + 3 · 0,7 + 3 · 0,3 = 6,0 с`.

### 3.2 Обработка через subprocess

Для каждого типа действия запускается отдельный дочерний процесс. Процессы работают одновременно, а запросы одного типа обрабатываются внутри своего процесса последовательно. Для запуска используется модуль `subprocess` и отдельный файл `worker.py`.

Время модели определяется наиболее долгой группой запросов, но к нему добавляются затраты на создание процессов и обмен результатами.

### 3.3 Обработка через threads

Для обработки запросов используется пул потоков `ThreadPoolExecutor`. Каждый запрос выполняется в отдельном задании пула. Пока один поток ожидает завершения операции, другие потоки могут выполнять свои задания.

Такой вариант удобен для операций, в которых значительная часть времени уходит на ожидание ввода-вывода.

### 3.4 Асинхронная обработка через asyncio

Для каждого запроса создаётся асинхронная задача. Функция `asyncio.gather` запускает задачи совместно, а `await asyncio.sleep` позволяет event loop переключаться на другие задачи во время ожидания.

Асинхронный вариант не создаёт отдельный поток или процесс для каждого запроса.

## 4 Оценка вычислительных и ёмкостных затрат

Обозначим общее количество запросов через `N = U1 + U2 + U3`.

| Вариант | Временная оценка для данной модели | Дополнительная память |
|---|---|---|
| Последовательный | `O(N)` | `O(N)` на список запросов |
| subprocess | `O(N)` суммарной работы; параллельное время зависит от самой долгой группы и накладных расходов запуска | `O(N)` и память дочерних процессов |
| threads | `O(N)` суммарной работы; при достаточном числе потоков ожидание выполняется одновременно | `O(N)` на задания и потоки |
| asyncio | `O(N)` на создание и обработку задач; время ожидания близко к максимальному времени отдельного запроса | `O(N)` на асинхронные задачи |

В этой программе `sleep` используется для моделирования времени обслуживания, поэтому сравнение показывает эффективность параллельного ожидания. Для вычислительных задач, нагружающих CPU, результаты будут другими: потоки Python ограничены GIL, а `asyncio` не распараллеливает CPU-вычисления.

## 5 Реализация программы

- `src/main.py` — ввод параметров, формирование запросов, четыре способа обработки и измерение времени.
- `src/worker.py` — обработчик группы запросов, запускаемый через `subprocess`.
- `Makefile` — запуск программы командой `make run`.

Используются стандартные средства Python: `time`, `subprocess`, `concurrent.futures` и `asyncio`. Дополнительные библиотеки не нужны.

## 6 Результаты запуска

Демонстрационный запуск выполнен для `U1 = U2 = U3 = 3`, `T1 = 1,0 с`, `T2 = 0,7 с`, `T3 = 0,3 с`.

| Способ обработки | Измеренное время |
|---|---:|
| Последовательный | 6,004 с |
| subprocess | 4,381 с |
| threads | 1,004 с |
| asyncio | 1,003 с |

В последовательном варианте время близко к сумме длительностей всех запросов. В вариантах `threads` и `asyncio` запросы ожидают завершения одновременно, поэтому время близко к длительности самого долгого запроса — 1 секунде. В варианте `subprocess` заметно влияние накладных расходов на запуск отдельных процессов.

Измерения зависят от компьютера и текущей нагрузки системы, поэтому при повторном запуске значения могут отличаться.

## 7 Вывод

В ходе лабораторной работы создана программа для моделирования запросов пользователей к серверу. Реализованы и сравнены последовательная обработка, запуск дочерних процессов через `subprocess`, многопоточность с `ThreadPoolExecutor` и асинхронная обработка с `asyncio`.

В выбранной модели ожидания наиболее быстро отработали `threads` и `asyncio`. Последовательный вариант оказался самым медленным, поскольку каждый запрос ожидал завершения предыдущего. `subprocess` также позволил выполнять группы запросов одновременно, однако запуск процессов добавил накладные расходы.

Таким образом, выбор способа обработки зависит от характера нагрузки. Потоки и асинхронность удобны для большого количества операций ожидания, а отдельные процессы могут использоваться для изоляции и параллельного выполнения независимых задач.
